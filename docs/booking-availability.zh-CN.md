# 预约和排班可用时间

[English](booking-availability.md) | [Русский](booking-availability.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

共享的 `BookingTimeFields` 构成部分用于快速详细情况和服务站的预约以及共用的维护创建/编辑形式。

- 在选定了日期和工位后,会装入被占用的间隔.  当参数发生变化时,取消了先前的请求 。
- 占用间隔内没有起始时间 。 只有在当前选择间隔内每分钟不能使用时,一个小时才会被完全封锁。
- 结束时间与所选开始的整个间隔时间相匹配 。 约期于11时结束,但不妨碍下次约期于11时开始。
- 一个提示显示占用的间隔,车牌,以及服务.  在移动时,可以提供可扩展的可用性清单。
- 在保存前, 手动输入和已选择的间隔会在可用性重新加载后检查 。 装载出错不作为可用的工位处理 。
- 在编辑期间,不包括目前的预约。 被取消和被删除的预约不占用任何时间。
- 服务器侧检查保存仍为强制 。 界面不能替换它 。

## API

`GET /api/v1/maintenance/occupied-slots?organizationId=…&date=2026-09-11&location=Пост%201&excludeMaintenanceId=…`

认证和该组织的 `MaintenanceView` 需要许可。 被排除在外的预约身份证是可选的。 响应不会被日历页面大小所缓存或限制;它包含 `id`, `startMinute`, `endMinute`, `vehicle`,以及 `service`. 分钟从计划日期起算。

可用性加载和冲突确认使用 `OpenCRM.Modules.Maintenance` 模块规则。 时间安排和可用性均使用计划日期,而不论状况如何。 实际完成日期在历史和报告中使用,不将预约日期挪至另一个日程日.  对于没有计划日期的遗留预约,这两项请求都采用主要预约日期。 工位名称在将相邻的白空间进行裁剪后会比较出大小写不敏感.  如果结尾缺失,则适用现行规则:开始后一小时.

 多天可用性和全部API日期范围如下: [期限规则](maintenance-periods.zh-CN.md).

<a name="statuses-and-dates"></a>

## 状况和日期

| 状态 | 可用的过渡 | 完成日期 |
| --- | --- | --- |
| 计划 | 开始工作, 完成, 取消 | 隐藏和未保存 |
| 进行中 | 完成、 取消、 返回计划 | 隐藏和未保存 |
| 已完成 | 返回确认状态, 编辑数据 | 显示和可编辑 |
| 已取消 | 继续预约,选择日期 | 隐藏和未保存 |

 在正常的工作流程中,按照计划产生新的预约。 现有预约使用卡片上的“完成”行动完成:实际日期记录不变,计划日期不变。 编辑器不提供不支持的过渡;服务器也通过编辑器任意改变状态来防止完成和倒置过渡. 倒转过渡使用单独的卡动作. 恢复取消的预约检查

简化后的服务站模式允许工作完成后创建. 编辑保留了原有地位并分开了实际日期;并不自动完成被取消的或主动的预约,也不以计划日期取代实际日期.

照片、服务、材料和计算仍然是历史的一部分,包括被取消的预约。 工作完成文件仅供已完成的工作使用。

<a name="verification"></a>

## 核查

`OccupiedMaintenanceSlotsTests`  请检查postgreSQL查询的组织,日期,工位,状况,排除编辑后的预约,500个记录上不得截取,读取数据前的授权.

 其他检查包括计划日期和实际日期不同时的日历/可用性一致性、在创建和编辑期间拒绝重叠、有效地位过渡以及通过“完成”行动记录日期。 浏览器假想涵盖三个客户端的所有四个状态并简化了服务站模式.

<a name="card-actions-and-reverse-transitions"></a>

## 纸牌动作和倒转

下一个步骤在牌头中突出:计划预约的“开始工作”,正在进行中的“完成”,被取消的“恢复预约”。  其他行动可通过“行动”提供。 状态变化需要确认; 如果失败, 对话框会保持打开并显示服务器响应 。 取消或返回时可以添加到历史中 。 重新安排和恢复日期和时间,并检查可用性。

- `return_to_planned`:仅取自“进行中”;保留计划日期和时间并清除实际日期。
- `return_to_work`:仅取自“已完成的”;将预约退回工作,并清除实际日期。 它对当前里程的影响被去除并从所剩读取的再计算出.
- 两个命令都检查工位冲突,保存服务,相片,支付和材料,并被记录在历史中.
- 相关缺陷保留其独立地位:返回工作不会使已经解决的缺陷再出.  确认对话框在链接存在时明确声明了这一点 。
- API 使用现有的 `IApplicationUnitOfWork`:状态,历史,里程,以及调度任务同步在一个交易中被保存. 预约行被锁定,直到动作完成;在获得锁后,其状态被重新读取. 重复反向命令不会创建第二个事件.

分开 `MaintenanceServiceCatalog` 类被删除。 服务构成验证在 `OpenCRM.Modules.Maintenance`;通过快速预约获得现役服务; `IOrganizationScenarioCatalogService.GetActiveServiceAsync`.  新卡片界面在共享中 `MaintenanceCardActions.vue` ; 现有紧凑清单行动部分保留。
