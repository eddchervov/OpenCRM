# 维修厂与车队功能开发

[English](sto-fleet-development.md) | [Русский](sto-fleet-development.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

这份文件描述了汽车修理店和车队的共享域名模式.  新组织可用的情景由安装配置决定;隐藏情景不会删除现有的组织或其数据.

这份文件结合了目前的实施,之前记录的计划,以及新的产品方向.

 它是一个详细的域模型和开发序列,而不是当前任务的第二列表. 技术文献地图载于 [指数](README.zh-CN.md).

<a name="product-goal"></a>

## 产品目标

细节是主要发展重点;服务站位居第二. 车队目前作为服务站的复制品保存,可能存在小的场景差异. 行动、部件、维修时间表和利用的车队具体特点被推迟。 这份文件描述了服务站和舰队,但并没有给予它们优先于"细节"的优先权. 服务站和舰队特征不必出现在"细节"中.

改进工作,表演者,材料,缺陷和文件,应当使用共享服务站和舰队基金会.  一个服务站处理属于外部客户的车辆和该客户的订单. 舰队将这一过程用于自己的车辆,并可能在后来通过业务跟踪加以扩展. 讨论各自背景下的详细任务。  在改变服务站时,确保共享模块仍然为Fleet工作.  如果Fleet需要不同的模块,现在不要构建其自定义版本;在服务站进一步发展后再重新审视.

<a name="limitations-and-unfinished-work"></a>

## 限制和未完成的工作

1. 下一个服务间隔是从车辆总体的最后一次维修记录中计算出来的. 操作类型和状态不能确定参考点. 另一项工作或计划/取消的任命可能扭曲到期日期。 参见活动 `OrganizationWorkspacePlanningQueryService.cs` 和业务流程计划中的B3。  未使用的前 MVC 页面查询被删除;其算法不是一个当前应用程序的切入点.
2. 自动规划间隔取自规则的名称和说明. 特定车辆或部件上的具体作业没有结构化的时间表。  见 `OrganizationPlanningPolicy.cs`.
3. 车辆没有组件模型,工作行和缺陷与组件没有关联. `Maintenance.Details` 存储在 `MaintenanceDetails` 带有稳定行标识和明确顺序的表格。  见 `MaintenanceDetail.cs` 和 `MaintenanceEntityTypeConfiguration.cs`.
4. 引擎小时支持输入一个日期的总整数读取.  目前还没有单独的“白天工作”工作流程、班次记录或独立的日常使用记录。  见 `VehicleCounterEntry.cs`, `VehicleService.cs`,以及 `CountersSection.vue`.
5. 存在外传消息,但具体未确认自动发送维护提醒。  见 `notifications.md` 及第4.6节 `plan.md`.
6. 运行中的应用程序中的端到端服务站假想仍被确定为下一轮检查. 代码可用性并不意味着已确认部署版本中的操作。  见 `plan.md`.

 第4.6节中的旧项目 `plan.md`  关于缺少行ID和Vue表格中多种服务的损失需要审查: `MaintenanceDetail.DetailId` 和 `MaintenanceFormSection.vue`  现在处理上面描述的基本问题。  在关闭此项目之前, 请检查是否保存有多个服务且与旧数据兼容的现有预约 。 在执行和核查之后,更新第4.6节其他项目的状况。

<a name="determining-the-next-maintenance-reference-point"></a>

## 确定下一个维护参考点

使用现有的服务目录进行单个操作,如发动机-油料变化,滤波器替换,或制动检查等. 将TO-1和TO-2作为这些行动的模板。 一套设备可能包括另一套设备的操作,但实际操作的构成必须保存在维护记录上. 单凭一个定名并不能证实其所有行动都已完成。

将时间表与具体业务挂钩,并在必要时与车辆部件和车型/车型挂钩。  它按照日历,里程,或发动机时数,警告阈值,以及无历史记录的车辆的初始点来定义间隔.  例如,“每250个发动机小时或每年一次更换发动机油”。  一个 TO-2 模板可以包含此操作和附加的工作,并有自己的间隔.

 经确认操作后,在完成时可省取日期和相关计数读取.  这对车成为该车下起动日期的参照点。 完成TO-2只更新实际完成的操作的调度;取消的订单,未完成的工作,或不同的服务不会改变到期日.  如果缺少所要求的读取,请不要计算一个精确的反向的到期值.  对于第一个记录,允许初始日期和读取或明确指定的即将到来的阈值.

 对于Fleet,支持两种间隔类型:从上次实际完成起,到初始读取的固定阈值起.  例如:TO-1在250,500,750发动机小时,TO-2在10个发动机小时.  当TO-2在10:00完成时,包含的TO-1操作也算作已完成,而下一个固定的TO-1阈值为12:50. 间隔类型必须是明确的时间表设定,不得从“TO-1”或“TO-2”的名称中推断出。

<a name="next-maintenance-calculation-module--design-proposal-for-b3"></a>

## 下一个维修计算单元——B3的设计建议

 在单体内部创建维护规划域模块,由服务站和车队共享:一个应用服务和计算器 `OpenCRM.Infrastructure.BL/MaintenancePlanning`中,结果合同 `OpenCRM.Services.Interfaces`. 第一阶段不需要一个新的项目、单独的程序、HTTP API和所储存的“下个到期日”表。  根据实际数据模型,在B3实施期间重审这一提议.

**模块边界 :** 装入组织和车辆数据仍保留在应用服务中;纯计算器接收一个结构化的时间表,确认的完成事实,当前读取,和计算日期.  它不访问数据库,发送消息,或构建接口卡. 应用服务验证组织所有权,并返回车辆卡、摘要、排程和未来提醒的一个结果。

**输入 :** 车辆和目录操作ID,可选组件; 带有日期和/或反间隔、间隔类型和警告阈值的规则; 初始值; 有日期和读取快照的确认操作完成; 有日期的当前读取。  一个服务名称或维护设置名称不是操作ID,也不是间隔的源.

**完成事实 :** 稳定 `MaintenanceDetail.DetailId` 已经存在,并且 `MaintenanceWorkOperation.Id` 对应它,但操作目前存储状态和 `CompletedAt`  没有阅读快照; `Maintenance.Mileage` 适用于整个命令。  对于一个可靠的参考点,为特定行提供单独的确认事件:组织,车辆,顺序, `DetailId`,目录操作,日期,和阅读快照单位。 将事件记录在确认结果的同时;确定B3执行期间没有表演者工作场所的订单的确认点。  对事实的纠正必须留下可以审计的历史. `Maintenance.Status == Completed` 单凭这一点并不能证明每一行都已完成。  对于没有这种事实的旧令,只使用确认的链接或明确的起首点,绝不从名字推断出.

**输出 :** 下一个起始日期和/或反值,剩余数额,说明“正常/即时/逾期/不充分的数据”,规则的识别和佐证事实,以及不确定性的原因。  对于反向到期价值,显示阈值和剩余数额;在数据支持费率估计数时,从利用率中计算一个估计日历日期,以后作为单独标注的预测。 以日历为基础的到期日与规定的日期和间隔日期仍然准确。

**执行:**  首先确定时间表和完成事实,然后涵盖部分完成的套件的计算案例,不同的工作,取消,更正,和缺失/存储读取. 接下去,将调度器和摘要从各自独立的计算器移动到共享服务,连接车辆卡,并仅再添加提醒.  不要将计算的日期存储为第二个真相来源;以后的任何缓存都必须从规则和事实中重新计算.

<a name="proposed-development-sequence"></a>

## 拟议发展顺序

<a name="1-verify-the-service-station-workflow-and-strengthen-shared-work"></a>

### 1. 核查服务站工作流程,加强共享工作

- 与测试组织一起走过:任命、服务、任务、执行、审查、付款、交接。 记录实际的UI和API相差.
- 检查多种服务、材料、价格、目录链接的保存情况; `DetailId`  当编辑新旧记录时。
- 固定维护的时间安排,以使用实际完成的所需类型的最后一次操作. 计划或取消的任用、加油、或根据另一时间表进行的工作不得重新确定到期日。
- 对排程器、摘要和车辆卡采用一次到期和紧急计算。

<a name="2-add-daily-fleet-operations"></a>

### 2.  每天增加车队业务

- 每辆车都让责任人每天快速进入:柜台阅读 ** 或者说** 那天引擎工作时数。 向试点用户确认他们实际从操作员那里得到的信息。
- 存储日期,作者,录入方法,以及校正. 输入日常利用率时,会计算产生的读取,而不会丢失原条目.
- 显示错失的天数, 和零利用率分开读取 。  在计算重置/重置计量时, 请检查重复值、 递减计数器和异常大值 。
- 从一个车辆总利用率数字开始。 添加单个组件计数器只用于真正拥有自身服务年限的组件.

<a name="3-add-components-and-operation-schedules"></a>

### 3. 添加组件和运行时间表

- 按车辆类型引入组件模板并允许每辆车配置。 将功能组件与已安装的单个部件区分开来;第一个版本不需要完整的部分跟踪.
- 将个人工作以及酌情将缺陷与组成部分联系起来。 保留旧记录,不提供组件。
- 配置特定操作的时间表:组件、日期和/或选定的对接间隔、警告阈值和参考点。  为第一项服务提供明确的初始价值。
- 计算第一个达到阈值的到期点; 显示缺失读取或呆滞读取的不确定性, 并将日历预测作为估计值标签 。

<a name="4-complete-fleet-management"></a>

### 4. 车队管理完成

- 向负有重复发送保护责任的人发出催复通知,并明确采取行动创建或开设工作。
- 按车辆和部件显示即将和已过期服务、开放缺陷、故障时间和开支的队列。
- 在存在可靠的操作到组件链接并经过核实的到期计算后,构建交互式组件图并进行高级分析.

<a name="criteria-for-the-first-useful-result"></a>

## 第一项有用结果的标准

1. 服务站力学和舰队力学使用共享过程;他们的卡片显示与每个场景相相關的字段.
2. 舰队用户每天通过车辆进入引擎时数,并可以看到当前读取的来源.
3. 完成的发动机-油改变只重新计算下个到期日;液压修理和被取消的订单不会改变.
4. 到期日与车辆卡,摘要和排程相匹配.  如果读取不充分,系统不会显示错误的确切日期.
5.  没有组成部分的历史工作仍然可以读取,而新的关系和计算并不暴露出另一个组织的数据.

<a name="decisions-to-confirm-during-the-pilot"></a>

## 试验期间确认的决定

- 哪些车辆可以起步:客车,卡车,或特殊用途车辆.  这影响了组件模板和计数器类型.
- 进入日常使用的人:操作员、机械师或调度员;是否需要批准和批量班次进入。
- 第一版机车是否需要分机时数和多台独立计数器.
- 第一分舰队发布时是否需要将维修与外部承包商联系起来。
