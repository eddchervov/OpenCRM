# 可选邮件验证

[English](email-confirmation.md) | [Русский](email-confirmation.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

电子邮件确认默认已禁用( E)`EmailConfirmation:Required=false`). 密码注册和登录不需要在基站安装中SMTP或邮箱确认.  要要求确认,首先配置和核实通知交付,然后设定 `EmailConfirmation__Required=true`. 旗帜本身不配置邮件发送 。

 以下限制只在此项政策生效时适用。  新用户和现有用户 `EmailConfirmed=false` 重定向为 `/auth/verify-email` 注册后。 其数据和成员保留;申请特征在确认前仍受限制.

 该页面使用共享的登录样式.  它显示时事账户地址,并要求用户打开收件箱并跟随电子邮件中的链接.  它提供“我确认我的电子邮件——继续”的再版,支持和退出行动。 活化剂和活化剂保护活化剂 `EmailDelivery` 政策;地址来自账户,而不是表格。

 在电子邮件排队后, 账户级别可适用60秒的冷却, 包括初始的注册电子邮件 。 按钮显示倒计时,在被按下后立即被禁用.  在联系邮件服务之前,服务器在解析时保留发送:并行请求,另一个分页,一个页面刷新,遗留的再发送路由在此间隔期间不会创建额外的电子邮件.  如果队列失败, 保留将被解除, 并允许再次尝试 。  以前发布的有效链接仍然可用以确认。

独立 `EmailDelivery`  每个IP地址每10分钟3个请求的限制仍然有效,并且也算作被压制的重复。  当达到限制时,所需的页面会显示一个消息并等待时间而不是JSON错误. 账户冷却被持有在当前进程的内存;重新启动应用程序可以清除. 多个应用实例需要共享的速率限制存储.

 经确认后,在同一届会议上再提出要求时,将取消限制。 前往主页可以保存正常的导航:现有成员被带入选定的组织;没有组织的用户被带入组织创建的开始阶段。 会员资格和许可检查一律适用;订阅限制只在商业模式下适用.

<a name="server-side-enforcement"></a>

## 服务器侧执行

 当政策被启用时, `EmailConfirmationMiddleware` 运行后 `UseAuthentication` 和之前 `UseAuthorization`.  对于有策略的路由,它首先评价认证部分通过 `IPolicyEvaluator` 承认JWTs,并采用正确的办法。  然后从数据库中读取时事账号:以前发行的cookie和JWTs不会绕过限制.

HTML 请求重定向到确认页; API 请求收到 HTTP 403 与 `code = email_confirmation_required` 和 `confirmationUrl`. 被禁止的行动,包括POST请求,不执行.

例外标记为: `AllowUnconfirmedEmailAttribute`:确认并再发,签入/注册,账号收回,签出/注销,账号删除,假冒回回,支持,法律文件,出错页,健康检查,以及公共静态资产. `AllowAnonymous` 单靠自己不足以绕过强制执行。 即便静态元数据否则允许访问,行政小组和杭火公司仍需要确认。

支持时,“新请求”按钮会在 `/personal/support/create`. 列表页面继续显示请求和所选择的对话. 成功提交随新请求返回到列表中;失败时,输入的值保留在表格中。 列表,创建表和回复不需电子邮件确认即可提供给已签名的用户. Antiforgery,请求创建限制和组织访问检查仍然有效.

重排被排除在一般提交加载器中,因为它自己的处理器管理按钮状态:捕获相中的普通处理器禁用按钮,而窗体处理器取消了与重复相同的请求. 运行 `site.js` 和 `email-verification.js` 一起保留预期行为:第一个请求会得到收益,一个重复被屏蔽,服务器的冷却被倒数倒计时,在到期时允许再次发送. 浏览器不检查邮箱是否存在,也不在电子邮件排队后更改倒计时;成功排队并不能保证发送到不存在的地址.

密码 `.auth-links` 排除普通链接的样式 `.btn`  因此,它们不涵盖成功确认页上的“继续工作”白文本。 `.auth-btn` 按钮将其内容集中在两个轴上。

`RequireConfirmedEmail` 和 `RequireConfirmedAccount` 故意仍然禁用:密码登录会为确认页创建一个有限制的会话. Middleware控制对特性的访问.  用电子邮件编码签名确认地址,并立即允许正常使用.

API的注册保留了它用符号的响应.  当启用此策略时, 它也会排队确认邮件 。  在确认前,这些令牌只允许列出的例外;应用程序请求收到HTTP 403. 未能发送电子邮件不能允许访问,而且仍可重新发送。

<a name="protection-boundaries"></a>

## 保护边界

证实需要访问邮箱,防止使用没有这种访问的伪造地址或他人地址。  它并不妨碍创建未经证实的账户记录,也不屏蔽可以接收电子邮件的临时邮箱.  对请求,电子邮件发送,以及失败的签名签名的独立限制仍然有效;CAPTCHA不是这个确认机制的一部分.
