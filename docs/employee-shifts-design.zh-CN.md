# 员工班次和工时

[English](employee-shifts-design.md) | [Русский](employee-shifts-design.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

> 详细介绍和汽车服务的一个解决方案是建立在现有的雇员和轮班模式之上。  以下各节区分了已经起作用的事物和仍然提出的事物。 相关指南列于本报告。 [文档索引](README.zh-CN.md).  以下拟议阶段是设计备选方案,而不是承诺的执行时间表。

<a name="at-a-glance"></a>

## 看着

1. 管理者维持本组织每周共同的雇员时间表。 代码已经支持创建、编辑和取消计划的班次、时区、观看自己的班次以及显示预定时间以外的分配工作。
2. 重复了前一周的情况,并在分配工人时增加了一个可用提示。 授权的HTTP检查完成;浏览器接受度仍保留在界面计划中. 详细和汽车服务根据雇员和计划的工作订单时间进行同样的计算。  它警告工作超过轮班时间,但不阻碍紧急工作。 缺少确切时间或用户无法查看时间表时,可用性未知.
3. 雇员执行今天分派的工作:开始、停工和完成一项行动并不取决于轮班标记。 手术间隔与工作时间不同。
4. 只有在确认需要后,才增加实际的起班和起班,并由每个组织单独启用。 普通的钟表事件不需要管理者批准;更正需要理由并保留历史.

 没有单独的“简单”和“先进”模式。 每周重复就足够5/2个时间表;2/2、3/1和其他轮换、休息、计时表、报告和薪金计算都超出了下一步。  对于不同的业务情景,共享模型和换行屏幕不会被重复.

<a name="goal-and-baseline"></a>

## 目标和基线

管理人员根据可用情况安排小组和分配工作。  在电话中,一个雇员看到下一班的轮班和他们的操作.  如果后来需要跟踪出勤情况,雇员可以不切换到单独的系统而打入和出勤;这一次仍与操作执行时间分开.

雇员简介已经存在,没有需要的账户,必要时可以与组织成员联系。 业务保留任务、状态、事件和工作间隔。 规划任务属于工作命令和客户关系管理行动。  因此,转移是一个单独的实体,与 `OrganizationEmployee`. 运行间隔不会自动填充一个计时表:它们不包括等待,准备,或操作之间的间歇.

统一的团队部分的相关设计,邀请,以及权限: [团队和接触](team-and-access-design.zh-CN.md).

解决方案由详细,汽车服务,和车队共同组成.  它不改变现有的工作订单权限,也不需要一个转向标记来执行指定的操作.

 当前代码引用 : [雇员简介](../src/OpenCRM.Domain/OrganizationEmployee.cs), [运行间隔](../src/OpenCRM.Domain/MaintenanceWorkInterval.cs), [规划员任务](../src/OpenCRM.Domain/OrganizationSchedulerTask.cs),以及 [雇员工作空间](../src/OpenCRM.Frontend/packages/workspace/src/components/WorkspaceWorkSection.vue).

<a name="implementation-phases"></a>

## 执行阶段

 第一个部分已实施:每周时间表、时间区选择、创建和编辑计划班次,并立即发布关于节省、取消、雇员对下一个公布的班次的看法,以及显示分配的维护,同时突出显示非临时时间。 重复一周和任务警告已编入代码,等待申请检查。  以下所述实际钟表事件、间断、无法提供、通知和报告仍然是分几个阶段的建议。

<a name="how-shifts-relate-to-maintenance"></a>

## 变动与维修的关系

轮班意味着雇员的可用性;维护是一项具体的任务。 创建换行不会自动指定工作 。 维护或服务不需要单独提供 `ShiftId`:屏幕从员工和计划时间计算关系.  如果一个工作命令或班次被移动,则不手工重新链接记录,对列表进行重新计算.

- 对于每项服务,工人是服务受让人,或者在没有选定服务受让人的情况下是主要工作订单受让人。 材料不是工作项目。
- 换班单元只显示分配的工作订单数量和出班指标. 点击打开时间表下方的单独列表,其中包含日期,雇员,车辆,以及时间等内容,并链接到工作订单卡.  如果按照一种工作顺序向不同的人提供服务,每个人都会看到自己的任务。
- 维护属于当其可靠的计划间隔与所分配员工的显示的班次相重叠时的班次.  对夜间工作来说,将当地时间表转换为组织的时区后,即时比较;维护日历日期不得直接与协调世界时的时段比较。
- 如果维修没有确切的计划时间,则显示“未设定时间”,不主张同一天轮班。 个人服务尚未有自己的计划间隔:整个维修期限不作为每个服务期限计算,也不作为工作量计算。
- 在分配或转移工作时,该间隔期间的雇员在工人选择者旁边显示。  如果已公布的班次只覆盖了部分间隔或不存在班次,则会出现警告. 用于紧急工作的备用活物;不把转换草稿视为确认可用。
- 实际运行时间与计划维修和轮班出勤时间分开跟踪。 移动维护不会重写已完成的操作历史 。 报告只计算一次工作命令和服务,即使工作跨越两班。

<a name="what-users-see"></a>

## 用户所见

<a name="simple-navigation"></a>

### 简单导航

管理者会在副菜单中获得一个单独的“屏蔽”项目。“团队”仍然是人员和访问设置清单。 员工的“我的工作”页面会为下一期公布的班次排出一行紧凑的内容。  没有常设的“时间表”和“报告”标签。

<a name="manager"></a>

### 经理

- “分离”本周开业,雇员分行和分行日。  一个单元格显示值班时间和维护时间短;细节和值班时间在时间表下单列。  主要行动是增加转变,并在上星期重复。 复制一天,在相关行动中可提供大宗行动。 组织营业时间为提示.
- 变换在形式保存后立即被公布. 雇员见公布的班级;增加和改变的通知属于后一阶段。 更年长的草稿可以通过打开和节省班次来公布.
- 在分配一项业务时,首先建议安排在这段时间的雇员。  如果被选中的人无法到达,则会出现一个简短的警告;紧急工作命令仍然可以指定。
- 出席问题不需要单独的屏幕:“审查计时事件”仅用于开放班次、缺失事件或更正请求并打开其清单。 管理者可以用其行中的原因来纠正一个事件.
- “团队”中的“精益摘要”将打开一个带一段时间过滤器的团队报告;在狭长的屏幕上,它出现在标题动作菜单中。  总的“统计”仍然是组织概况。
- 管理者可以在没有账户的情况下安排员工,并在需要时手动输入员工的实际时间.  这种记录被标记为进入管理器。

<a name="employee"></a>

### 雇员

- “我的工作”的顶端有一个紧凑的一行,有今天/下一班、小时和状态。  在电话中,按状态显示一项主要行动:“开始换班”、“开始换班”、“返回”、“结束换班”仍然是第二项可用行动。  行被隐藏,直到启用调度功能.  当启用没有时钟跟踪的调度时,它只显示计划时数.
- 结束轮班后,以出勤,休息,活动运行时间,并完成各项工作等内容进行简短总结.  这些金额有不同的标签,而且不会使主屏幕模糊不清。
- 如果错过了活动,雇员将开始轮班,并有正当理由要求更正。 管理者批准或拒绝。 雇员只看他们的日程安排、钟表和工作。
- 允许在预定时间以外开始安排不定期的轮班和工作;管理人员可得到审查项目。 网络重试不创建第二个时钟事件 。

<a name="employee-profile"></a>

### 雇员简介

简介将名称和联系方式,活动状态,账户链接,即将到来的班次,当前任务,以及简短的工作总计等结合起来. 成员角色决定了客户关系管理访问;工作职能和专业描述可以分配哪些工作.  这些概念分别被存储. 专业课程可在基本时间安排后作为可选任务提示而加入;不得放慢增加员工的速度.

 一个单独的“无法使用”区块让管理人员在不造成假班的情况下标记缺勤:休假、休假或其他原因。 原因仅能被获得团队管理许可的用户所看到;规划者只需要不可用状态. 雇员缺勤申请和批准可在基本时间安排后增加。

<a name="employee-without-an-account"></a>

### 雇员无账户

雇员可以在不进行登记的情况下分配工作和轮班。  他们不能使用自助时钟按钮. 管理人员既输入计划时间,也输入实际时间;报告标明来源。  如果一个账户在以后被链接,历史仍属于同一雇员。

<a name="data-model-and-rules"></a>

## 数据模型和规则

1.  为该组织存储一个IANA时区. 管理者在首次启用时间表时明确选择. 现有 `WorkdayStart`/`WorkdayEnd` 仍建议开放时间,而不是替代轮班时间。 改变时区保留了作为UTC间隔的现有班次,但会显示这些班次,并在新区中选择周. 计划的维护时间仍然是当地墙上小时数。
2. `OrganizationEmployeeShift` 存储 OrganizationId、IndustriesId、计划开始和结束(空到不定期的班)、计划中断时间、本地起始日期、时区快照、出版状态、实际开始/结束、实际时间来源和版本。 实际起止时间为UTC即时. 已公布的有计划的转变必须具有两种界限。
3. `OrganizationEmployeeShiftBreak` 存储实际中断间隔。 允许每班多次休息。 出勤时间为实际班次间隔减去间歇.
4. `OrganizationEmployeeUnavailability` 存储一个不可用时段和类别。 在此期间,新的转变或任务引起警告,但不删除现有历史。
5.  对已公布计划和实际时间的修改,在现有的组织审计中记录有作者、时间、理由和价值前后。 雇员时钟事件和人工更正是可以区分的。 行动日志中仍然有行动更正。
6.  一名雇员的计划班次不能重叠;单独班次的实际间隔也不能重叠。 雇员可能只有一个实际开放的班级和一个开放的休息时间。 休息时间必须在实际轮班之内。 并行请求由交易、版本和命令密钥保护。
7. 隔夜轮班仍然是整个午夜的一个记录,在每周时间表的每个受影响日都有出现。 出版物使用该组织当前时区的当地起始日期。 期间总数使用协调世界时的间隔与组织时区的期间界限相重叠。  在钟表变化期间,当地时间不明确或不存在,需要明确选择/更正表格。
8. 该系统没有默默地关闭开放的转变。  它出现在经理的例外名单中. 以开放休息结束一班,确认后在同一时间结束。
9. 雇员不能以公开轮班的形式存档;以往的轮班和任务在历史上仍然可以使用。 历史班次从未被删除;一个错误的计划被取消,并有记录的原因.
10. 开始,延后,完成一项行动 仍然独立于轮班时钟事件。 管理报告中标出在转变之外的工作;现有工作流程没有被阻断。
11. 班次启用前的历史作业保持不变。  就发射前的期间而言,计划和实际的转变值是“无数据”,而不是零小时。

## 访问

| 能力 | 业主/管理人 | 雇员 |  无帐户的雇员 |
| --- | --- | --- | --- |
| 共享时间表和时间表 | 单独的视图/管理权限 |  没有 |  没有 |
| 拥有已发布的时间表 |  对 |  对 |  没有注册 |
| 自助钟表和更正请求 |  如果与雇员简介相链接 |  对 |  没有 |
| 纠正他人的时间 | 单独的许可、理由和审计 |  没有 |  没有 |
|  全团队报告 | 报告许可 |  没有 |  没有 |
| 金钱、费用、赔偿 | 仅限财务许可 | 默认无 |  没有 |

 拟议权限 : `shifts.view`, `shifts.manage`, `shifts.self.view`, `shifts.self.clock`, `shifts.time.correct`,以及 `reports.employees.view`.  所有者和管理者默认获得共享权限;雇员只获得自己的权限。 对其他角色的许可被明确指定. 允许编辑员工配置文件本身并不允许更改时间表 。 服务器总是检查组织,链接员工简介,以及动作权限.

<a name="server-contract"></a>

## 服务器合同

- 按时间段和雇员阅读共享时间表;通过单独请求读取自己即将进行的和目前的班次。 员工们的反应没有其他人的转变。
- 创建、批量复制、编辑和公布计划班次;每个班次接受版本并记录审计事件。 冲突在批量行动前显示,确认的集合在解剖上被保存.
- 启动一班,开始/结束一班,结束一班的自助命令接受一个命令密钥进行安全重试. 事件时间来自服务器;客户端只发送动作和密钥.
- 正确实际时间,通过有需要原因的单独经理命令,为无账户的员工创建实际记录. 雇员更正申请在批准前不更改计时表。
- 报告使用服务器侧时间范围,并对每个输出列应用权限检查.  在服务器上用页码计算出长时间,而不是将全部历史加入浏览器.

<a name="reports-and-definitions"></a>

## 报告和定义

- “雇员工作一段时间”:雇员、工作命令、业务、完成日期、状态、活动时间、教养和返回。  对于已完成的工程,工期以作业完成时间为准. 历史调查必须分开:目前的“我的工作”仅限于最近完成的工作命令。
- “计划/实际”:计划时数减去计划间歇;实际出勤数减去实际间歇;偏差和校正来源。  它不把操作执行时间算作出勤时间。
- “工作量”:雇员和服务单位分配的工时和完成的作业数。 返回的作业不算作单独的作业命令。
- “材料”:雇员、业务和工作秩序的实际问题和回报。 成本和购买价格需要资金许可。
- 这些报告没有包括收入:服务价格和工作订单的劳动成本并不决定具体个人的工资。 薪金要求有一个单独商定的费率/佣金和校正模式。

 第一份报告从“小组”中的“实际摘要”开始:本月和所有雇员默认,然后按雇员、服务和状态过滤。  每个行链接到它的工作命令;CSV导出在许可检查后可以使用. 一份摘要和清单在电话上就足够了;详细表格是供桌面上的管理人员使用的。

<a name="rollout-phases"></a>

## 推出阶段

1. **时刻表没有强制性的时钟事件.** 组织时区,计划轮班,简单不可用时段,每周网格,每周副本,出版,自视,任务警示. 现有的执行工作流程一如既往地继续下去。
2. **实际时间和时间表。** 换行开始/结束,休息,无账户员工的管理者条目,更正请求,审计,以及例外列表. 自助计时是一种组织设置.  如果实际时间追踪中断,时间表和工作执行继续有效。
3. **报告。** 雇员的工作、计划/实际、工作量和质量。 财政专栏分别受财政许可保护.
4. **增上方便所缘.**  在预订客户时重复进度表模板,缺位请求,可选专业,以及工作量建议. 仅在检查球队如何使用第一阶段后添加这些.

<a name="compensation-as-a-separate-phase"></a>

## 赔偿作为一个单独阶段

 在商定业务规则后,增加计算补偿:有效日期规则(每小时费率、每次业务的固定数额或百分比)、人工更正并说明理由、批准期限和付款历史。 计算基数必须明确:经批准的班次时间或已完成的作业. 改变费率不会重新计算未经单独行动而已经核准的期间。  这是内部组织计算,而不是人力资源或会计的取而代之。  在这些规则存在之前,服务价格和劳动成本不作为雇员的收入显示。

<a name="verifiable-scenarios"></a>

## 可核实的假设情景

- 一名经理从熟悉的雇员名单切换到时间表,一周在一分钟内复制,更换两班并公布;一名雇员只看到他们的新周。
- 员工开始一班,分两次休息,完成多起操作,并结束一班;计时表和运行时间显示不同的,正确的总数.
- 夜间轮班和过夜行动出现在正确的日期,报告没有重复计算。
- 网络故障后重试时钟动作,不会产生第二次转会或中断.
- 没有计划轮班的雇员可以从事紧急工作;管理人员认为有例外。
- 附表上列有没有帐户的雇员;以管理人员为单位的实际时间标明其来源。
- 员工无法改变他人的轮班。
- 老年工作订单出现在工作报告中,而计时表则显示该功能启动前的“无数据”。
