# 服务目录完整性

[English](service-catalog-integrity.md) | [Русский](service-catalog-integrity.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

 一个组织的记录可以将目录服务与捆绑与几个任意的工作结合起来. 任意工作需要姓名、数量和价格; `CatalogItemId` 仍然为空,没有自动创建目录项。  如果提供了ID,服务器验证服务是否存在,属于组织,有正确的类型,并且是可用的.  没有组织的现有个人账户记录保留其以前的行为。

快速详细情况和服务站的任命将工作组成情况送交 `Services`; 旧的 `ServiceId`  在列表缺失时支持兼容性。 连载: `CatalogItemId`,服务器使用目录名称。  对于任意的工作,它会保存输入的名称. 预约卡同时返回名称的ID和文本快照. 价格仍然是这项特定工作的商定价格,不受未来目录变化的影响。

 当编辑一个具有相同ID的现有行时,服务器保留了它的历史名称. 存档服务只允许在现有行上;存档服务不能作为附加行被添加.  在名称相同时改变链接的做法也持续存在并被记录在历史中。

 删除服务存档,包括从未使用过的服务. 身份证从不重复使用。 档案服务在历史上仍然可用,可以恢复.  其他目录类型的规则不变.

<a name="forms"></a>

## 表单

- “选择服务”打开模板 `services` 和服务捆绑。“海关工作”为手工输入添加一行,并可以多次使用。 `workTypes` 包含过程阶段,不能替代服务。
- 初始服务仍在数据库中通过下列方式创建: `OrganizationScenarioCatalogService.EnsureDefaultsAsync`;表格中不包含内置倒计时列表。
- 完整表单在预约时编辑所有服务,考虑每行的总数,不失去第二行或后期服务.
- 一个空的 `CatalogItemId` 是指定制工作. 提供但无效的ID仍然被拒绝 。 添加模板将保留所有先前输入的行 。
- 选择对话框中的“ 编辑” 在新标签中打开相关的服务或捆绑目录, 同时保留窗体 。  当用户可以访问目录时,链接就可以使用.
- 已归档的项目被标记为“存档”;在重新命名之后,将显示其历史名称和现在的名称。

<a name="existing-data"></a>

## 现有数据

 在自定义工作被允许后, 缺少一个 `CatalogItemId` 单靠自己不是一个错误。 遗产恢复脚本不得再被应用到所有没有链接的行上.

数据库计划没有改变正常化: `CatalogItemId` 已经存在于 JSON 列中 `Maintenance.Details`;将行移入表格是通过下面的常态迁移完成的.

1. 备份数据库并运行 `scripts/maintenance/audit-service-links.sql`.  它只读并包括历史记录和被删除的组织记录;个人记录和材料不包括在内。
2.  审查情况: `can_link` 意味着一个匹配, `not_found` 意味着没有匹配, `ambiguous` 意味着多种服务, `invalid_link` 指身份证没有指向该组织内的服务,以及 `linked` / `archived` 意思是链接存在。
3. 脚本只链接到没有在同一组织中具有完全一个同名服务的ID的行上,忽略了大小写和周围的白空间. 已归档的项目计为历史匹配 。 名称、价格、说明和行顺序不变。 脚本是交易和可重复的;现有的无效链接不是被覆盖的.
4.  再做一次审计  通过在编辑器中明确选择服务来解决所剩案件。 不得根据类似名称进行猜测,或自动将“接受”等阶段转变为服务。

使用备份来撤销链接恢复:脚本不会将原始链接存储在单独的表格中.

“维持”是指试验数据的一次性正常化,而不是应用行为。  在正常化时,API需要明确的服务选择;现在也允许定制工作。

<a name="verification"></a>

## 核查

`MaintenanceServiceCatalogTests` 检查在 PostgreSQL 上通过服务保存: 不存在、 外国和存档的 ID 和 阶段; 在不创建目录项的模板的同时自定义工作; 历史名称和价格; 多重服务; 仅更改一个ID; 防止在服务无效时创建车辆 。 SQL检查覆盖了存档项目,模糊名称,另一个组织,阶段,无效链接,保存其他数据,并重复执行.

浏览器检查覆盖所有三个客户端,创建和编辑,保存ID,多行,存档项目,一个空目录,光/暗主题,宽度为320–1440 px.

## B. 包组组成和其他结构化领域——要求

<a name="bundle-composition"></a>

### 套装组装

`OrganizationScenarioCatalogItem.ServiceIds` 被存储为 `uuid[]`,不是JSON。 贾森。  这些是目录项目之间的关系; 组成已移到 `OrganizationServiceBundleItems`. `ValidateServiceSettingsAsync` 内 [CatalogCommandService.cs (中文(简体) ).](../src/OpenCRM.Modules.Catalog/CatalogCommandService.cs) 已经验证了组织内1至100个不同的活跃服务。 阵列元素上缺失的外国密钥是存储模型限制,而不是缺乏服务级验证. 移徙决不能削弱现行规则。  目前,通过目录归档一个服务会留下一个包含在编辑器中的不可用内容的捆绑,而组织设置则会防止包含在活动捆绑中的服务失效. 入境点之间的这种区别不是通过增加外国钥匙来固定的;在执行之前,决定是保留每个入境点的规则,还是商定一个单独的任务来统一这些规则.

执行标准:

1. 关系包含 `BundleId`, `ServiceId`,并保留原数组顺序。 `(BundleId, ServiceId)`  在捆绑中的位置是独一无二的; 捆绑检查由 `ServiceId`  有合适的索引。  现在不要添加数量:目前的模型包括一次服务,而订单数量是一个单独的概念.
2. 现有目录记录的参考点. 捆绑和服务属于同一组织,并有预期的 `KindCode`. 仅凭ID上的外国密钥并不能执行这两条规则:在设计过程中验证了chema保护方法并保留了服务验证.
3. 服务或捆绑的存档保存关系. 仍禁止重新使用带不可用服务的捆绑,现有订单行、名称、价格和数量不重新计算。 修改现有的规则来编辑带有存档服务的捆绑,需要一个单独的域任务.
4. DTO/API的答复继续回放 `ServiceIds` 以原顺序。 更新捆绑阅读、创建和编辑、组织设置期间的服务使用检查以及会计数据导出。  请检查所有三个客户端的共享消费者:显示、选择、可用性、持续时间和防止重复行。  不扩展单独的“细节”进程。
5.  在迁移前, 请检查已保存的数组是否为空捆绑, 重复, 缺少的ID, 另一个组织, 不正确的类型, 以及其它类型记录的数据 。 仅一个存档服务并不意味着一个被损坏的链接.  不自动删除或替换无效行;在应用限制前记录并决定如何解决.
6.  在保留位置的同时移动所有有效关系; 比较前后的构成和顺序, 包括存档捆绑 。  在删除数组前定义与旧应用程序版本的相容性和放行命令 。 向下必须按相同的顺序还原数组;明确描述回滚时的任何数据损失. 检查 EF 迁移属性, 设计器, 快照, 以及根据项目规则进行最后有效的相邻迁移 。
7. 构建, 运行已存在 `BundlesReferenceOnlyActiveServicesOfTheirOrganization` 和时间/目录 PostgreSQL 检查,并构建受影响的客户端。 由于没有对PostgreSQL的迁移核查,该项目仍未核实;比较SQL和建筑物不能替代迁移数据。

`OrganizationServiceBundleItem` 和 `OrganizationServiceBundleItems` 保持组成和地位。 外国密钥已过 `(Id, OrganizationId, KindCode)` 和固定类型的检查 强制组织界限。 位置独有性使用一个被推迟的 PostgreSQL 约束, 这样命令就可以在其中更改 `SaveChanges`  没有中间冲突。 EF保留了常规指数;迁移维持了SQL的制约.  这次迁移不需要新的数据存取抽象。

<a name="moving-order-rows"></a>

### 移动顺序行

`MaintenanceDetails` 包含 `(MaintenanceId, DetailId)` 键,位置,以及所有以前的行字段。 命令的外键仅在物理命令删除时删除子行;软删除保留. 名称、价格、表演者和材料仍然是历史的快照。  可忽略目录的ID仍然保留原样:现有审计和恢复允许遗留的无效链接.  这些历史ID上的外国密钥现在还没有被引入;它需要单独的协议和对旧数据的验证. 与已完成的操作、照片和报告的链接 `DetailId` 被保留下来。

收集更新由 `DetailId`保留跟踪EF行和订单转换检查。 `Position` 定义命令; 位置独有性使用被推迟的 PostgreSQL 约束。 搜索与报告读取行表;验证和清晰的链接-恢复脚本被更新用于新的计划. API继续还原之前的DTO.

<a name="work-bays-closure-and-history-preservation--verification"></a>

## 工作工位、关闭和历史保存——核查

 一个预约目前使用文本链接到一个工位 `Maintenance.Location`.  因此,一个从未使用过的自定义湾可以被更名或删除,而一个曾经使用的湾只能被关闭并重新开放. 历史名称不能指定为不同的新工位 。 使用过的工位从不被物理删除;关闭它不会自动取消或移动其预约. 关闭前,界面列出未完成的任务,并警告必须手动移动.

 以下项目是根据独立审计确定的:

- 两个同名的活跃的新工位曾经是相隔一行,但代表了一个调度能力. 创建、重新命名和恢复现在检查占用的活跃和历史名称,忽略了周围的白空间,置于组织锁下。  同名并存的创作只保留了1个工位. 现有的重复不自动合并或删除.
- 先前任用的封闭工位仍保留有“关闭”标记的详细服务站时间表,但没有为它们提供新的空档。  根据先前的以字符串为基础的合同,仍然可以使用一个与已关闭工位同名的活跃后遗工位。
- 关闭的工位不能再通过重新安排现有任命来预订。 共享检查适用于全版编辑,预约重新安排,单独更新日期,并将一个被取消/已完成的预约恢复到占用一个档位的地位. 拒绝不会改变日期,状态,版本,行,或历史. 允许编辑评论/价格,而不进行新的预订,开始和完成现有工作;预约可以移到另一个活动工位.

服务保留了之前的合同:更改目录名称,价格,或持续时间不会重新计算被保存的订单或时间表;归档防止了新的服务行并保留了旧行.  删除一项服务意味着将其归档,包括未使用的服务;ID和历史快照依然存在. 装有存档服务的捆绑必须固定其组成才能再次被使用.

Real PostgreSQL检查覆盖了目录,所有路线的重排限制,以及历史服务行的保存;界面被单独对照一个演示API检查. 缺少一个旧的目录测试容器 `VehicleRegistrationPlatePolicy` 配置;真实配置在测试固定中被注册,没有生产配置变化.

重新命名一个用过的工位仍然是目前模型的一个限制. 安全支持需要稳定 `WorkPostId`,一个单独的历史名称, 并检查旧的模糊的任务。

覆盖范围包括重新命名和删除未使用的工位的正值检查,仅改变时间,并通过共享格式重新开放。  这些结果不包括一个完整的、有真正Billing的终到终工作日。
