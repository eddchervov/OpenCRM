<a name="languages-and-dictionaries"></a>

## 语文和词典

共同客户模块 `@opencrm/ui/i18n` Vue I18n; 服务器页面和验证使用 ASP.NET 核心本地化 `.resx`. 桌面管理员使用单独的 `.resx` 和可观察的束缚。 资源对应不同的执行环境;服务器通过JSON向旧的JavaScript传输词典而无需手动复制脚本中的密钥.

语言登记册规定了代码、正确名称、默认格式、文本方向和翻译准备情况。 初始设定 : `ru`, `en`, `zh-Hans`. 区域格式另行界定,例如 `ru-RU`, `en-GB`, `zh-CN`. 浏览器头 `zh-CN`  必须允许使用支持的简化中文; `zh-Hant`  它没有被宣布为现成的翻译。

字典分为主题领域:一般行动,账户,客户,汽车,时刻表,工作,仓库,财务,行政管理.  例如,关键来描述意义。 `clients.actions.create`. 句子全由有名参数翻译;数量形式由语言规则决定. 用户的文本及其实体名称无需翻译即可保存。

来宾语言选择:在饼干中明确选择,然后支持浏览器语言,再选择英语.  对于登录的用户,保存的明显偏好优先;更改语言更新配置和cookie.  对于现有的用户,在过渡期间保留俄语.  不支持的语言根据登记处的明确规则提供给已知的版本或保留语言。

服务器在第一次显示前将允许的语言传输给客户端应用程序.  在Razor,Vue和adminka之间的过渡时,语言被保留. 第一步,改变语言可以重新装入当前页面:这使得调和服务器文本和下载数据更容易.  未保存的表格需要标准保护,防止输入丢失。  所有 Vue 实例,包括 Razor 页面上的内置字段,都收到相同的设置 。

En 准备就绪后保留的语言为英语.  在单个段落的转移过程中,允许俄文备份文本,但该部分不视为被翻译. 组装检查申报的现成字典的完整性,参数和数量形式等. 缺乏翻译不应向用户显示内部密钥.

API出错获得稳定的主题代码和参数. 客户端不比较消息的文本. 过渡会保存现有的响应字段和状态;服务器向其他API用户提供本地化消息. 技术例外不直接被翻译为用户翻译.

 该组织的历史现在已具备 `Title` 和 `Description` 输入 `OrganizationAuditEvent`. 新的系统事件必须保持一个稳定的类型和结构化的参数,以读者的语言显示。 旧有的现成行和用户描述在没有自动翻译的情况下被保存;这是EN和汉语全覆盖的明显例外. 事件参数中的货币价值和时间保留了原始交易的货币和上下文.

来信和通知是基于接受者的语言,而不是当前流的文化.  对于没有概况的外部客户,则使用其明确偏好或该组织通信语言。 更改语言时, 用户模板不会被覆盖 。  对于重复发货,所选语言或成品内容按照现有的发货机制录入.

 全覆盖内容包括公共页面,登录,注册,恢复访问,个人账户,所有CRM脚本,网页和桌面管理员,具备可用集成功能的助手,出错,提示,调度,输出,打印表格,信件和通知等. 审计中还包括工作组成部分和内置的图书馆对话框。 “OpenCRM-基于”的签名及其参考文献按照现行项目规则予以保留;强制性签名的翻译要求单独商定项目条款。

## 组织货币

 第一个版本支持每个组织一种会计货币。  拟议领域 -- -- `CurrencyCode` 并检查所支持的货币代码目录。  该符号仅用于显示. 用户区定义了分隔符和符号位置,组织的货币决定了总和的单位.

个人设备和服务可以在没有组织的情况下存在; `MaintenanceFinancialTotal` 空头 `OrganizationId`. 这一领域需要一种单独的个人会计货币,一旦有货币数据,这种货币的变动限制相同。 该文件明确保留其通用语;不能取自语言或目前的开放组织。 车辆在您的个人区域与您的组织之间行驶,并不改变您的历史证件的通货.

货币文件和交易保留其货币代码;如果模型不允许货币混合,则文件行从文件中继承. 服务器检查价格、仓库成本、付款、收益和债务是否与组织的货币相符。  按货币开列的若干组织的报告。  没有单独的换算模式,不同货币的总和加起来不会达到一个总数。

 根据目前的模型,存储保持精确的小数或最小单位。  在支付和总额中考虑分数的货币;单位价格和成本的内部准确度可能更高.  四舍五入的规则是固定在行,税,总额,回报和与提供方的交换. 以新的通用类型取代所有的钱田并不是第一阶段的必要部分.

 只要没有依赖性的货币数据,包括价格、成本平衡和初始债务,货币变化是允许的。 验证由服务器在调整设置后的协调交易中进行。  一旦有了数据,正常的班次就会被阻断. 以几种货币转换现有组织、汇率和结算是一个单独的阶段;用美元取代统一汇率签名是不可接受的。

OpenCRM订阅费保留了提供者自己的货币和支票。 CRM货币不会自动更改. 进出口明确传送货币编码;与实体不匹配需要错误或单独转换的情况。

## 国家和登记号

 该组织的国家定义了新形状的初始值,但没有定义每辆车的国家. 机器上加了一个单独的注册国;允许有一个未知的国家,包括组织外的个人设备。  一个显然未知的国家是一个代码。 `ZZ` 它使用自由的Unicode编号,与前作不同. `null`. 旧记录和 API `null` 或保持俄语规则为空; 更改语言不会覆盖此相容性。  新表显示RU为初始选择,向"Condate Unknown"报告ZZ的过渡. 编辑旧机器所剩的字段不会取而代之. `null` 自动在RU上。

 对于前俄罗斯数字,维持现有的服务器政策. 外国数字和明显不明的国家的ZZ通常使用 `InternationalRegistrationPlateRules`免费Unicode代表最多24个字符,去除极端空格并检查不可接受控制字符. 类似字母的俄文替换不适用于这些字母. 常规表格、快速入境和进口都使用规则;国家核查是在建立相关客户之前进行的。

 您需要将数字的原始表示和规范化的搜索密钥分开 。  俄罗斯对类似字母的比较只在国家统治规定的情况下适用. 平话和外语字母不会丢失. 口罩是一种提示;对于特殊,临时和未知格式,免费输入提供安全长度和字符限制.

查找和识别复制品时,要考虑组织和国家,必要时还要考虑注册地区和号码的类别. 未知国家线路的巧合不会导致自动组合出车. 快速录制,导入,API,助手,汽车编辑器和个人用具都共享相同的服务器政策. 客户端上的缓存格式按国家和版本的规则划分.

国家规则加上数据集和测试,而不在屏幕内横跨全国。  对CN来说,在严格核查之前,需要按数字类别和专家核查公布来源;通用输入允许您工作,直到一套完整的口罩准备好.

一项单独的审计涵盖电话、姓名、地址、指数、税收和银行细节、里程和数量单位、目录、文件模板和综合。 语言支持并不意味着自动支持当地的税收和支付系统. 不得在TIN和检查站作业场放置中国的必备物品。 新的计量单位需要有一个明确的值单位和重新计算历史的规则.

<a name="preparation-of-the-chinese-interface"></a>

## 中国界面的准备

目标选项是 `zh-Hans`  为中国大陆服务. 术语词典记录了客户的翻译、上诉、记录、订货、工程、仓库和付款情况,然后才进行大规模转移。 EN也通过文字编辑,以免将模糊之处转移至下一种语言.

中文已经在第一阶段的试验屏幕上进行了测试:入口,客户端,汽车和订单出道. 检查通过 IME 传输、按钮宽度、字符串高度、搜索和输入。 键盘处理器在复合字符完成之前,不应保留形状或更改搜索. 名称不需要拉丁文,也不需要部分之间的空格.

界面字体和PDF生成器必须包含中文字符. 检查它们的可用性和许可证是否自我安装;没有强制从外部CDN下载。 打印的表格通过视觉检查,包括表格传输和文本突出显示。

<a name="transition-of-existing-data"></a>

## 现有数据的过渡

1. 编制货币实体列表,时间字段,出错代码,目录,以及用户模板. 将现行限制和目标规则分开。
2. 添加相容字段并读取旧数据 。 准备背景任务,DTO,行政客户端,导入,导出并恢复备份.
3. 只有在核实现有货币数据是否与目前的卢布会计有关时,才应指定为卢比。 数字数额保持不变。  不使用浏览器的语言定义货币 。
4. 省省时区.  对于未说明的,不通过服务器位置指定一个区域,也不重新解释历史日期。  在安排时间表之前,需要在需要带子的地方作出明确的调整。
5.  不默认指定所有旧车 RU 。 保存数字,突出确认格式,未知国家和密钥相撞;进行质量校正,另作可核查操作.
6. 重新计算搜索密钥而不删除正本;检查链接保留,历史,并重复条目.  对于过渡期,确定对新旧视图的兼容搜索.
7. 只有在对所有录制组件商定更新后才能启用新设置。 旧版本不应创造没有货币的金额,也不应对外国数字适用先前的正常化。

 每个迁移必须匹配 EF Core 版本和相邻的项目迁移:主文件,属性,设计者和快照一起检查. 试验过渡和重新启动是在非个人基础上检查的。  在外国数字或金额以其他货币出现后删除新字段不视为安全回滚;您需要数据保留计划和兼容的应用程序版本.
