# Subscription payments and self-employed receipts

**English** | [Русский](admin-finance.ru.md) | [简体中文](admin-finance.zh-CN.md)

This guide describes the optional commercial module. It is available only when `PlatformPolicy:Commercial:Enabled=true`; the setting defaults to `false`. A deployment must configure its payment provider, notification service, Hangfire, and private file storage before using the corresponding workflows.


Before purchasing or renewing a workspace plan, the buyer states whether they are acting as an individual or on behalf of an organization/sole proprietor. For an organization or sole proprietor, the legal name or sole proprietor's full name and a 10- or 12-digit TIN with a valid checksum are required. The selected details are saved in the payment record when it is created. The workspace name alone does not determine the buyer type. Legacy payments retain the `unknown` type.

The admin section “Finance” → “Payments and subscriptions” → “Purchases and self-employed receipts” lists confirmed purchases without limiting results to the first 300 payments. Cancelled payments remain in payment history but are not counted as purchases, even if an old, incorrect payment date was stored. The list shows the buyer, TIN, user, plan, amount, payment date, and payment status. Records can be searched and filtered; the interface shows payment count, total amount, and the number of paid receipts not marked as issued. The 30-day total and payment count use the confirmed payment date; the amount is net of refunds. Cancelled attempts are not revenue.

After creating a receipt in “My Tax” and giving it to the buyer, an administrator with `Admin.Billing.Manage` manually marks it as issued. A reason is required to add or remove the mark; changes are recorded in `admin.NpdReceiptAudits`. The mark does not create a receipt with the Federal Tax Service or send it to the customer. The purchase card can store an HTTPS receipt link on an FTS domain, a comment, and one PDF, PNG, or JPG file up to 5 MB. The file is stored in the existing private S3 storage and downloaded only through an authenticated admin route. Detaching removes the file reference from the payment; the object remains in storage for now because the shared provider reuses files by hash.

## Automated monitoring

The purchase table shows paid payments with unmarked receipts first. An age over 24 hours is highlighted as an internal monitoring target, not a statutory deadline. The admin interface displays a warning with the number of such payments and paid payments with activation errors. The counter loads when the admin interface opens and refreshes every minute; the warning links directly to purchases and self-employed receipts. Telegram is not used for this channel.

The “Send receipt” button queues an email to the user's registered address through the existing notification queue. If a file is attached, the email contains a protected download link valid for 30 days; replacing or detaching the file invalidates the old link. If no file is attached, the saved FTS link is sent. The table separately shows queueing, acceptance by the email service, confirmed delivery, and errors. Repeating the same request does not create a second email; sending can be retried after an error. After a successful send, a new receipt version requires replacing the file or link. Marking the receipt as issued remains a separate administrator action.

Every 15 minutes, a background job reconciles a limited batch of payments with YooKassa. For a payment whose webhook was lost, it checks the ID, amount, currency, and remote status, then runs the same subscription activation path as the webhook. Paid payments with activation errors are not reactivated automatically and remain in the review queue. If YooKassa confirms cancellation without payment, reconciliation clears an erroneous payment date and removes the record from the purchase list; active subscription access must be checked separately. Reconciliation also records partial and full refund amounts; the table shows gross payments and the amount after refunds. This automation does not issue refunds or correct self-employed receipts.

The `AddBillingAutomation` migration adds the refund amount, reconciliation date, and pointer to the latest receipt email. Existing payments initially have a zero refund amount, which is updated after reconciliation with YooKassa. Rolling back the migration deletes this data history. Scheduled jobs and email delivery require a running Hangfire, PostgreSQL, notification service, and configured file storage.

The payment creation request for a self-employed seller does not include the `receipt` object used for receipts under Federal Law 54-FZ: the self-employed receipt is issued separately in “My Tax”. YooKassa confirmation through the existing flow activates the plan and records the successful payment date. Demonstration and manual free grants do not create payments or self-employed receipts.

The `AddPaymentBuyerAndNpdReceipts` migration adds a buyer snapshot, payment date, receipt details, and an audit log. For older records with `completed` status, the payment date is reconstructed from the status-change date or payment creation date; it may be approximate. `Down` deletes this data, so rolling back after real sales have taken place loses receipt history.
