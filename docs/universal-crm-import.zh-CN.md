# CRM 数据导入

<a name="modules-and-entry-point"></a>

## 模块和切入点

向导位于选定的组织设置中,并使用共享 `packages/workspace` 详细情况、服务站和舰队部分。
服务器侧包生命周期、文件解析、匹配、准备和应用程序日志属于 `OpenCRM.Modules.Imports`.
历史订单、服务项目、付款和事件都是通过专门 `IImportBusinessRecordProcessor` 合同中 `OpenCRM.Modules.Maintenance`.
HTTP 控制器和背景处理器在 `OpenCRM.WebApp`. 向导合同目前正在执行 `OpenCRM.Services.Interfaces/Imports`.

<a name="supported-data"></a>

## 支持的数据

- 客户和车辆,包括外部客户身份证的链接。
- 历史顺序 `completed` 和 `cancelled` 各州。 主动订单及其时刻表不被导入.
- 服务/工作线:名称,说明,整数,单价.  每个命令至少需要一行.
- 单独支付,包括被取消的支付:金额,日期,方法和被取消日期. 活期付款不得超过订单总额。
- 历史事件有原始日期,文字,和作者.  在OpenCRM中,它们被明确标记为被导入的事件.

使用日期 `YYYY-MM-DD` 或 ISO 8601;没有抵消的时间作为协调世界时处理。
数量不使用千位分隔符,小数点和百分率精确度;限度是 `numeric(18,2)`.
服务线也遵循了正常的维护规则:数量从1到10000,线路总数不超过99999999,没有HTML,最多可有1000个字符.
顺序总数必须等于行数减去折扣后的总和。 库存流动、目前的通知、收据和银行业务并非由历史进口所触发。

订单的买方和付款人不从车辆目前的所有人推断出来。
`partyName` 存储历史名称。  可选 `partyClientId` 将其链接到同一软件包中允许的客户,或链接到以前从同一源数据库中导入的客户;对于此链接,必须明确提供历史名称。
 如果没有源链接,则只保留文本快照或未知值.

<a name="files-and-mapping"></a>

## 文件与绘图

 新包接受 CSV, XLSX, ZIP 包含 CSV, 或限制文本 SQL 导出最多可达 50 MB 和 100,000个源行跨表.
 每个表格最多可有100列,每个单元格可有10,000个字符,还有200MB的已解开的XLSX数据. Excel公式被拒绝.
客户和车辆的后遗症同步HTTP合同保持了之前的10个MB5000行的限值;表格使用新批的API.

ZIP将多达100个非空CSV文件合并为一个包,并有共享关系. 已拆出的总尺寸限于200 MB,每张CSV为50 MB,归档条目包括文件夹为200.
 文件直接从存档处被读取,而不取出到磁盘;被嵌入的档案,ZIP内部的SQL,可执行文件,以及出走文件夹的路径被拒绝.

SQL 文件总是被解析为数据. 仅支持这些格式:

- `INSERT INTO table (column, ...) VALUES ('text', 123, NULL, ...);`,包括多发多发多发.
- 文本 PostgreSQL `COPY table (column, ...) FROM stdin;` 终止日期 `\.`.

INSERT字符串使用双倍单引号;COPY支持标准文本逃出序列.
SQL 执行, DDL, 程序, 表达式, 二进制堆放, `.bak`,恢复另一个数据库,不支持不支持的方言。
使用带有明确列的只包含数据导出;未知的命令会以明显的错误停止准备.
 这不是每个CRM schema的适配器:用户在向导中验证每个表格类型和关系.

自动映射仅限于明确的已知信头.  可以手动选择并合并列.
重建已准备好的行需要单独确认,因为它会丢弃手动编辑.
连接订单需要外部车辆ID;线路、付款和历史需要外部订单ID。
 一个历史顺序限制在1000个孩子行,这样就可以整体应用.

 每个被映射的字段都可以有明确的转换: 以初始的俄语 8取而代之为7的电话数字,一个允许准确格式中的一种日期,一个没有使用一个周期的空格的小数,或者一个源/目标字典.
 一个字典帮助地图状态和从另一个客户关系管理中支付的方法.  一个未知的字典值或另一个格式中的日期会停止准备并识别表格,行和字段;任意程序不会被执行.
转换后的价值在确认前的定期可编辑审查中提供.

 一个个人组织简介存储了头条结构,映射,变换,以及源名,但不出口行.
配置文件仅适用于相容的表格结构,在重建前需要确认;列顺序被检查.
作者每个组织最多可拥有50个剖面图;在解剖学上再次以同名保存来替换设置.  只有作者可以查看或删除它们.

 在确认前,向导显示对新记录、已完成订单的总额、活期付款和未清余额进行初步核对。
重复,排除行,取消订单,取消支付不会增加财政总额.  如果存在出错,则总计为临时的;导入时被屏蔽到固定为止.

<a name="processing-and-recovery"></a>

## 处理和追回

`OrganizationImportDrafts` 存储软件包状态和版本。 源行、候选人和临时文件分别储存在 `OrganizationImportSourceRow`, `OrganizationImportRow`,以及 `OrganizationImportFile`.
 这些表格中的JSON是源数据和制备快照的格式;工作客户,车辆,订单,行和支付都是在常规关系模型中创建的.
 在解析成功后,临时文件在原子上被删除,同时保留准备的表格.

 该表单每页最多要求100名候选人,并从源表格中预览最多20行.
搜索和过滤器运行在服务器上.  只保存当前页面上已更改的行;然后进行背景检查来重新计算关系和软件包摘要.
 确认和进一步编辑被屏蔽,直到检查结束.
 未保存的更改也被复制到 `sessionStorage` 用于当前用户、组织和软件包版本。
与服务器不同的本地版本不能被自动应用;在被明确删除之前可以作为 CSV 下载.

`OrganizationImportWorker` 处理在与 HTTP 请求无关的小步骤中坚持的队列。
PostgreSQL 咨询锁保护一个包跨进程. 应用每批货物及其日志标记是一件交易。
订单:客户 车辆 包括线路、付款和历史在内的完整订单总量。
典型的批次包含多达250名顾客/车辆或500行订单;大型单项订单从不在交易之间分出.
 每批货物在组织锁下的交易中解剖应用。  在每页新客户或新车辆之前,对配额进行重新计算,以核算已经建立的记录; 自由限制包括从接口中移除的存档车辆和客户.
 如果另一个操作在页面之间消耗了剩余容量,则在插入之前会停止下一页;完成的页面仍然保存. 软件包以某种理由进入被暂停状态,在容量解脱或数据调整后可以恢复;再试不会再创建已经应用的行.
 每批货物之前都要重新检查客户/车辆的许可、配额和现状。 将更改的结果退回审查。

应用程序重新启动后, 数据库中将恢复未完成的任务 。 重复确认或恢复一个软件包并不重复其记录。
分批暂停。 已经应用的行只读;剩余行在继续前可以被更正和检查.
历史订单要求源CRM数据库有一个稳定的名称(`SourceKey`由所有出口品分享。 名称通过修剪和对大小写不敏感比较实现常态化.
同一客户关系管理产品的不同数据库必须使用不同的名称。  文件名不是源标识符;导入开始后源不能被更改 。
永久关系登记处 `OrganizationImportIdentity` 存储一个独特的组织、来源、记录类型和外部识别密钥、与客户/车辆/订单的输入链接,以及SHA-256所准备数据的指纹。
外部身份识别不敏感地匹配。 以源模式进口的客户和车辆需要外部的ID;一个没有ID的目录CSV可以在没有源代码的情况下被导入,使用普通的手机/VIN/平板检查,没有交叉文件注册.

匹配当前记录的密钥和内容链接 。 被更改的源数据或被删除/无法访问的目标产生冲突,而不重写当前卡片或历史.
将历史秩序与包括工作、报酬和事件在内的整体相比较,以维护工作秩序。 匹配的聚合整体被跳过, 即使它比正常批量大 。
 新订货可以指以前从该数据库进口的客户和车辆. 仅将付款或历史添加到先前的订单中是不支持的;必须通过单独的更新程序调节全部总量。
注册外部ID,创建业务对象,并记录日志标记发生在一次交易中;在申请前在组织锁下重复检查.
先前在没有来源的情况下进口的包件不会自动被添加到登记册中:其来源无法可靠地从文件名中确定.

 全球没有在已经完成的批次中回滚。 部分结果明确显示;完整的CSV报告包括源链接,数量,日期,目标ID,以及每行的应用时间.
软件包和日志不会被自动删除,保存所创建的记录的续作和出处.

<a name="access-and-migrations"></a>

## 出入和移徙

基础向导需要配置管理、客户/车辆视图和创建以及关系管理权限,并需要相关订阅模块。 `PlatformPolicy:Commercial:Enabled=true`.  在默认的基准模式下,不需要付费计划;会员资格和权限仍然执行.
应用命令需要命令查看/创建权限和命令模块;支付需要财务查看/管理权限和财务模块.
作者可以读取和准备自己的文件,并有基础访问. 另一用户的软件包可能包含尚未分类的财务信息,因此查看或修改该软件包还需要全程订单和融资访问。
 每条路由都标到所选组织;动作作者来自当前认证的账户. 写出HTTP请求是被防伪保护的.

需要的迁移 : `AddOrganizationImportDrafts`, `AddOrganizationImportBatchStorage`,以及 `AddImportProfilesAndSourceIdentity`.
将第三个移回则删除剖面图和交叉文件源登记册,同时保留工作记录和软件包。  这将删除跨文件保护; 在再次导入前需要单独核对 。
倒转第二次迁移删除行级草稿及其日志;自动转换回旧的JSON格式是不可能的.
已创建的商业记录仍然存在;回滚计划不会抵消已经完成的导入。 后退包后回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回回部分的部分部分的回回回回回回回回回回回回回的回回回回回回回回回回回回回回回回回回回回回回回回回回回
检查临时 PostgreSQL 的迁移, 而不是在工作数据库中 。

试行每个新客户关系管理的第一个真实出口:检查关系结构、状况、历史买家、订单总额和付款总额。
10万行限制是一个安全约束;它不能保证每个文件或服务器配置的处理时间相同.

<a name="administrative-crm-import--integrity-fix"></a>

## 行政客户关系管理进口——完整性修复

 这是一条与通用向导不同的行政路径: `/api/v1/admin/crm-import/*`.  它的服务和文件解析现在属于 `OpenCRM.Modules.Imports.Crm`; 接口和现有的 DTO 字段仍在 `OpenCRM.Services.Interfaces.Imports`. `ManagePermissions` 政策、路线、CSV/JSON/XML, `CrmImportBatch`,以及 `RowsJson`/`ResultJson` 格式被保留。

预览仍然选择一个用户及其组织.  在确认时,选定 `batch.UserId` 用于验证会员资格; 实际管理人取自认证的 `NameIdentifier` 并分别通过. 客户和车辆历史 保留管理员, `EventType=imported`, `RelatedEntityType=crm-import`,以及 `RelatedEntityId=batch.Id`. 事件不会被反馈到历史包中。

 确认首先锁定组织,然后是包,并重新检查源行并允许车辆计数. 车辆的制造使用组织的共享 `IVehicleLimitQueryService`: 缺少 `VehiclesView`  对于选定的成员,不改变管理工作流程。 仅限客户进口并不需要车辆容量,也不叫这一支票。  没有增加限制的例外情况。

客户、车辆、历史和包件结果保存在一个交易中;最后的保存失败卷回更早的插入。 反复确认仍是冲突,不再产生记录. 单独的包竞争同一个组织能力;在获得锁后会检查限制. 数据库计划和公共JSON没有改变。
