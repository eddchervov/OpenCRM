# Shared CRM Shell

**English** | [Русский](crm-workspace-shell.ru.md)

The shell is used by the detailing, auto service, and fleet clients. The public website and administration interfaces do not use it.

The current style is the foundation for further CRM development. New screens and changes to existing screens should follow this design:

- Full-width workspace, left navigation, and a compact top bar.
- Calm neutral surfaces, fine borders, and an orange accent; light and dark themes are equally supported.
- Compact forms, cards, and charts. A wider screen gives content more room instead of making controls taller.
- Breadcrumbs in the form heading; the last item is the current screen title and is not a link.
- Actions beside the relevant data, without unnecessary buttons or explanatory labels.
- Users see actions available to them. An employee without permission to manage a plan sees its expiry status without a payment prompt.
- On phones, content fits the viewport width and navigation opens in a separate panel.

Vehicle registration fields use the shared Maska library and server-side `VehicleRegistrationPlates` configuration. The same configuration defines letter and digit positions for passenger and commercial vehicles, trailers, motorcycles, and tractor-style plates. The vehicle card and both quick-booking forms use `VehicleRegistrationPlateInput`; personal Vue 2 forms use the shared `v-registration-plate` from the built bundle. “Other plate format” preserves foreign or non-standard spelling; vehicle types without a mask use free-form input. An unchanged legacy plate does not prevent editing other fields. Search accepts a partial plate and finds old Latin, Cyrillic, and mixed spellings without rewriting history.

Pasting a value or changing its type must not silently turn it into a different plate by dropping unsupported characters. The server also validates before saving. `vehicleRegistrationPlateCoverage.test.mjs` scans Vue and Razor sources to check that the shared mask is connected to every editable plate field and that the bundle is present on personal pages. Standard Russian formats check positions and the letters АВЕКМНОРСТУХ without querying the registry of issued plates; even a correctly formatted voice-recognized plate must be reviewed by an employee in the draft.

The current implementation of shared components is the styling reference. Extend it through the shared palette and components so detailing, auto service, and fleet remain consistent. A change in visual direction requires a separate decision with the user.

- `packages/workspace/src/components/WorkspaceCrmShell.vue` — full-width workspace, pinned top bar, organizations, profile, and mobile menu.
- `packages/workspace/src/components/WorkspaceCrmNavigation.vue` — sections, groups, icons, and active item. The same component is used on desktop and phones.
- Each `Scenarios/*-client/src/App.vue` provides context, its sections, and breadcrumbs. Routes and work-screen content remain in the scenario client.

Detailing and auto service navigation is grouped by daily work, customers, resources, reports, and help/access. The server context defines groups and order; permissions and route codes are preserved. When returning to appointments, the current user and organization retain date, period, view, bay, slot duration, and bay-view search. See [implementation, checks, and limitations](navigation.md).

In a maintenance card, stages adapt to the width of their content, and tabs wrap without horizontal scrolling. Form errors appear beside the relevant field, are associated for keyboard use, and move focus to that field; a summary at the bottom supplements the inline explanation. Implementation and verification are documented separately.

New sections are added through the existing scenario section list and server-context menu. The top bar has no “Create” button. Organization creation is available on “Organizations,” while appointment actions remain in their corresponding work sections. No scenario has a separate menu item for creating maintenance or a work order: creation starts from a button inside the appointments section. `maintenance` form and card routes remain available for these actions and direct links. The shell does not grant permissions; server access checks remain mandatory.

Module availability does not depend on the plan: basic access restricts data changes through read-only mode. In settings, Import remains visible with an explanation and disabled upload; the working import form does not start in this mode. Organization archiving manages its lifecycle: it is available with `workspace.archive`, regardless of read-only mode or subscription, and uses normal confirmation. This is recoverable archiving within the retention period, not physical deletion.

## Accessible date and time fields

Shared `UiDatePicker` and `UiTimePicker` were refined: the date field has an accessible name independent of the open calendar content, and month-change buttons are named through the standard v-calendar slots. The time field is associated with its label through `UiFieldLabel.forId`; if no custom `id` is provided, stable `useId` is used. Value model, localization, limits, and read-only checks are preserved.

When changing the `UiDatePicker` wrapper, account for v-calendar 3.1.2 lifecycle dependence on focus: moving to an outer `div` exposed `dayIndex` when closing after a date selection. The final change kept the original wrapper and uses ARIA. Reproduction, option comparison, and verification limits are documented in the interface review record.
