# 支付服务集成

[English](payments-service-integration.md) | [Русский](payments-service-integration.ru.md) | **简体中文**

> 本页为机器译稿。涉及部署、接口或数据变更时，请同时核对英文或俄文原文。

OpenCRM的个人和组织订阅一次性购买和续订整合. 工作室的工作订单获取、自动支付和退款后的权利变更不属于这一范围。 退款被记录为金钱事实; 管理员修改已经允许的访问 。

<a name="source-of-state"></a>

## 国家来源

付款拥有YooKassa的要求、存储钥匙、货币事实、退款及其数据库。 OpenCRM拥有购买条件快照、受益人应享权利和访问补助金。 应用程序通过单独的RabbitMQ vhost交换合同;两者都不直接访问对方的数据库.

OpenCRM在网络访问前将购买,支付和不可改变的命令保存在一个交易中. 客户端接收了HTTP 202并购买Id. GET /api/v1/pays/ surprise/{ surpriseId}只提供给购买者;结果页使用准确的ID. URL或付款并不意味着订阅已经激活 。

收发箱重复了原始的ID和正文;收发箱验证了ExactId和版本. 受益人的预订会阻止同时进行的不相容采购。 计划条款和特征在创建时即被概括;续订时,即适用GrantedFrom。 订阅补助金和应用程序在锁定受益人和购买时共同承付。 付款后重审应享权利申请后数据库失效,而不是收费。

历史付款保留了PersviderCode=yookassa和上一条路线。  新采购使用支付服务。 旧的处理器,调节器和人工货币状态的改变不会修改这些购买.  通过微服务接受的购买在网络故障或配置变化中永远不会回落到旧的网关上.

<a name="refunds-and-manual-review"></a>

## 退款和人工审查

 在准许进入之前,全额退款,不启动就停止购买。 给予区块自动激活前的任何部分退款,需要审查. 给予后全部或部分退款不缩短认购时间;购入后收到退款_要求_存取_审查. 失败或未知的退款作为单独事件持续存在,包括Command, OperationId, Status,以及安全错误代码,而没有替换确认的金额.

OpenCRM收到退款确认和失败. 受权管理人可通过下列所述保护行动要求退款: [署长的行动](#administrator-actions); `RequestRefund` 是通过金融信息箱发送的。 人工输入的状态不是提供者确认的退款。 授权、数额确认、一能和提供者的对账仍然是强制性的。

## 移徙和回滚

OpenCRM 添加了 20261025071834_AddPayments ServicePurcases; 支付追加了 20261025140000_HardenPaymentExecutionAndAudit 和 20261025180000_Add Provider Operation PostBefore. 验证主文件, DbContext/ migration 设计器, 快照, 和 HasPendingModel Changes 。 货币快照/命令不受修改。  当购买/命令/事件存在时, 禁止为新的 OpenCRM 计划下架 。 禁止以财务审计或方式不明的方式向下支付硬化付款; 禁止在下岗后,接受的操作有期限。  一个空的图案允许技术回滚;从不自动回滚一个活动的数据库.

 要停止销售,请使用 Accept NewPurchases=false with Delectiond= true并重新启动兼容的OpenCRM版本. 端到端测试涵盖待购买 —— 重新开始,新采购受阻 —— 新采购被拒绝 —— 先前采购成功 —— 一次准入赠款。 已启用=虚假禁用所有财务运输,适合空/未连接环境;当存在任何微服务购买,包括应用服务购买时,使用Eulated=虚假启动被屏蔽,因为延迟退款仍需监控.

应用程序回滚不得使已接受购买的消费丧失功能,或允许直接收费。 保留回收服务或停止新采购,直到有兼容的版本。 备份数据库和RabitMQ 在您自己的发布程序。 恢复一个数据库的旧备份需要核对另一个数据库、供应商和登记册;尚未在登记册中自动发现所有丢失的采购。

## 行政部门的付款记录

微服务记录将确认的金钱,退款,以及历史授予的准入期分开.  每个货币事实都显示了管理员的下个动作. YooKassa身份证与内部微服务身份证分开。 日记默认会倒闭;事件有清晰的标签,代码会单独扩展,没有巢卷. 手动微服务状态替换无法使用 。 未知的购买ID 显示没有结果, 而不是取代上次成功的支付; 取消的购买不会激活访问 。 重复 POST 与原始密钥/ body 创建没有第二个支付对象, GET 则完全没有创建对象. 订阅的导航打开正确的受益人列表,包括停止订阅.

<a name="server-setup"></a>

## 服务器设置

基站安装保持商业模式并禁用付费运输.  要出售平台订阅, 配置自己的计划, 启用 `PlatformPolicy:Commercial:Enabled`,并分别连接付款。 工作订单付款跟踪不需要这种整合。

1. 单独提供具有非超级用户角色的服务数据库,私人RabbitMQ vhost,以及限制性服务账户.  通过仓库外的保护配置来提供秘密.  在升级前备份两个应用程序数据库并保存数据保护密钥.
2. 开始于 `YooKassaTest`. 匹配商号 `Payments:IsTest`,以及 OpenCRM 软件 `PaymentsService:ExpectedIsTest`. 运行模式需要 `YooKassaLive`, `IsTest=false`,匹配的活键,以及 `ExpectedIsTest=false`仅改变一面旗帜是不够的。
3. 内部支付API保密. 使用 HTTPS 或明确允许仅通过精确的内部主机名 `PaymentsService:InternalHttpHost`;需要共享服务密钥。 仅显示必要的供应商召回, `/webhooks/yookassa`,通过您的 HTTPS 代理。  不检查前一个安装的路线或网络地形, 不要重复使用 。
4. 应用两种应用程序的迁移,并在接受购买前开始其消费者. 验证准备状态、消息代理许可、命令/活动交付以及在服务中断后恢复。 使用 `AcceptNewPurchases=false` 停止新采购,同时保留已接受业务的处理。
