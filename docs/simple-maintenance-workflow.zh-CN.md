# 美容门店与维修厂共用流程

<a name="behavior"></a>

## 行为

 在“工作与时间表”设置中,“简单/按阶段”模式可用于详细信息和服务站。 未来以简单方式的访问将按计划保存下来,并占用一个工位。  该卡显示一个主要“抓好”按钮;中间阶段、服务线状况和总体完成指标被隐藏。 仍可通过行动重新安排、取消和恢复任命。

“移交”打开确认,然后完成工作,并将移交记录在一份请求中。 任何未清余额单独显示;交接不产生付款或改变到期金额. 实际跟踪的未完成业务和未解决的额外工作继续阻碍移交工作。 指派雇员不从事任何业务,并不要求完成假的阶段。  如果存在实际作业或调查结果,则仍可使用其部门来解决限制问题。

 在再次移交先前完成的记录时,保留其实际完成日期和先前记录的准备状态。 达到计划日期本身并不能完成这项工作。 现有的撤销移交行动仍然可用,需要说明理由。

两种设想的日历表都明确表明打算作出计划的任命。  对于遗留的 API 客户端,没有新的 `IsPlannedBooking` 安全地表示有计划的任命。 明确 `false`  在简单模式下,用于进入已经完成的工作;在分阶段模式下,仍计划快速创建任命。 表格还选择了在输入未来日期时的计划情景。

舰队保留了以前的工作流程。 旧工作验证中现有的"细节"例外没有收紧;改变一个组织的模式不会迁移地位或以前订单的历史.

<a name="architecture"></a>

## 建筑

 没有新的表格或迁移。 实施工作利用了现有的 `MaintenanceStatus`, `CompletedDate`, `ReadyForHandoverAt`, `HandedOverAt`、历史、服务和付款日志。

密码 `simple_handover` 命令贯穿现有的交易维护服务,并检查组织、当前模式和情景, `maintenance.edit`,组织和记录锁,和记录版本。 关闭相关缺陷,在实际完成时同步计数器,并保留调度器同步. 原子交接后,不会排出任何错误的“准备移交”信息。

<a name="automated-checks"></a>

## 自动检查

- 有针对性的维护检查包括过渡,移交,历史日期保存,访问,版本,操作守卫,以及副作用等.
- 组织快速创建的HTTP检查覆盖了细节和服务站,两者都是模式,明确意图,以及没有新领域.
- 完整的前端套件涵盖共享模式的可用性,动作,带有版本,出错的单一交接请求,以及写作限制.
- 细节和服务站客户端构建,WebApp构建成功;已存在的NuGet和编译器警告仍然存在.

<a name="browser-and-database-verification"></a>

## 浏览器和数据库校验

校验使用全WebApp中包含真实的API和PostgreSQL在单独的测试数据库上,并应用了迁移;生产数据库没有被使用. 环境参数(运行地址、容器和数据库)来自测试设置本身的配置。 共享通知使用内移;外部客户端bots和分析器被禁用;支付和S3设置为测试值.  本通行证没有检查照片、外部消息和获取情况。

已用临时工具编制了合成所有人和测试计划。 两个组织、工位、服务、时间表和任命都是通过真正的接口建立的。  这是带有真实API和PostgreSQL的完整WebApp,而不是带有演示API的前端预览.

| 浏览器方案 |  结果 |
| --- | --- |
| 细节: 启用简单模式 | 设置已保存; 卡片加载后可使用简单的动作 。 |
| 详细情况:未来的任用、间隔、工位、定价服务 | 任用是“计划”;间隔时间被占用并被排除在可用起始时间之外。 |
| 细节:重新装入并移交 | 重新装入后显示一个按钮; 确认会立即保存交接, 不另设启动/ 完成/ 准备动作 。 |
| 细节: 重新装入 | “搁置”、实际时间、已付款、服务余额保持不变。 |
| 服务站:简单模式,未来预约,服务 | 计划状况和占用时间在时间表中得到确认。 |
| 服务站:重新装入后移交 | 一次操作;在重新装入后,“手提”,0已支付,余额与服务价格相等。 |
| 服务站:改为“分几个阶段”,另行任用 | 仍有四个阶段和“开始工作”按钮。 开始的工作被节省;在重新装入后,“进行中”是积极的,可以随时移交。  未进行多次演出者的全面操作。 |

详细内容被从光和暗的主题来看,服务站也被从狭义的浏览器区域来看.  这不是每个屏幕宽度和角色的完整矩阵. 角色限制和出错路径也通过自动化测试进行额外检查.
