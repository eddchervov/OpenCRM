# Запись на несколько дней

Одна запись содержит плановый период, услуги, автомобиль, клиента, фотографии и расчёт. Создавать отдельное обслуживание на каждый день не требуется.

## Даты и время

- `PlannedDate` + `PlannedStartTime` — плановое начало.
- `PlannedEndDate` + `PlannedEndTime` — плановое окончание.
- `CompletedDate` — фактическая дата выполнения; изменение статуса не подменяет ею плановый период.
- Даты хранятся как календарные даты в принятом проектом формате. Отдельные поля времени не преобразуются в другой часовой пояс.

По умолчанию начало и окончание относятся к одному дню. Например, можно выбрать начало 10:00 одного дня и окончание 18:00 через два дня. Для нескольких дней обязательны оба времени. Окончание должно быть строго позже начала; ошибочный период больше не заменяется молча на часовой.

Однодневная запись без времени сохраняет прежнее поведение: показывается среди записей без времени и не резервирует пост. Если передано только начало однодневной записи, сервер сохраняет окончание через час, включая переход через полночь.

## Занятость поста

Выбранный пост занят **непрерывно на всём периоде**. Дни сушки или хранения тоже входят в этот резерв. Отдельные интервалы работы на разных постах внутри одной записи в этот этап не входят.

Пересечение определяется условием `startA < endB && startB < endA`. Если одна запись заканчивается в 11:00, другую можно начать в 11:00. Окончание в 00:00 не занимает следующий календарный день.

Проверка выполняется при создании, редактировании, переносе и возобновлении записи. API сохранения использует существующий `IApplicationUnitOfWork`. Внутри транзакции блокировка PostgreSQL сериализует проверку и сохранение по организации и нормализованному имени поста. Это защищает и от одновременных запросов на разных днях пересекающегося периода.

Отменённые и удалённые записи не блокируют время. Завершённые записи сохраняют плановую занятость в расписании: фактическое выполнение не переписывает первоначальный план. При редактировании сама запись исключается из конкурентов.

Форма проверяет весь диапазон через `occupied-slots?date=...&dateTo=...`. Ответ содержит абсолютное начало и окончание для подсказок и смещения в минутах от первого дня для выбора времени. Серверная проверка остаётся обязательной, даже если интерфейс ранее показал свободное время.

## Интерфейс и связанные данные

- Быстрое создание детейлинга и СТО, полный редактор, перенос и старые личные формы передают дату окончания.
- При переносе сохраняется число дней периода. Дату окончания можно скорректировать отдельно.
- Календарь выбирает записи по пересечению с видимым диапазоном, включая начавшиеся раньше него.
- Слоты обрезают только отображение границами выбранного дня. В базе остаётся полный период.
- Карточки записи, клиента, автомобиля и список расписания показывают многодневный период.
- Рабочий день отличает продолжающуюся запись от прошедшей; у продолжающейся работы с окончанием в выбранный день показывается соответствующая подпись.
- В PDF и Word плановый период указан отдельно от даты выполнения.
- Услуги, оплаты и материалы остаются в одной записи. Правила расчёта и финансового учёта не менялись.

Доработан существующий общий механизм обслуживания; отдельная сущность многодневной записи или новый сервис не добавлялись. Публичные страницы сайта не менялись.

## Миграция

Миграция: `20260913120000_AddMaintenancePlannedEndDate` в `OpenCRM.Infrastructure.Migrations`.

Она добавляет nullable-колонку `Maintenance.PlannedEndDate` и заполняет её существующей `PlannedDate`. Длительность старых записей не придумывается. Метаданные миграции, Designer и snapshot согласованы с Entity Framework Core 10.0.7.

Перед запуском нового кода миграцию необходимо применить к его базе. Старый код совместим с добавленной nullable-колонкой. Откат `Down` удаляет колонку и поэтому теряет даты окончания новых многодневных записей; для отката приложения колонку лучше сохранить.

## Проверки

Интеграционные тесты используют временные PostgreSQL 15 и RabbitMQ через Testcontainers, а не рабочие базы и очереди:

- однодневные и многодневные интервалы, переходы месяца и года;
- занятость промежуточного дня и исключительная граница окончания в полночь;
- соприкасающиеся интервалы и конфликты;
- перенос, редактирование без потери даты окончания и откат конфликтующего изменения;
- два одновременных бронирования одного поста;
- применение миграций и отсутствие расхождения модели со snapshot;
- независимость фактического завершения и планового периода в рабочем дне.

Дополнительно проверяются TypeScript/Vue-сборка, функции выбора времени и преобразование многодневных событий во всех трёх календарях.
